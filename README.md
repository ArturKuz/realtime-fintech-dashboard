# Realtime Fintech Dashboard

An Angular application with a live market dashboard and producer settings. Simulated market data is
generated by a WebAssembly module (written in AssemblyScript) running inside a Web Worker.

- **Live demo:** <https://arturkuz.github.io/realtime-fintech-dashboard/>
- **Repository:** <https://github.com/ArturKuz/realtime-fintech-dashboard>

**Dashboard** — one row per instrument with last price, bid–ask spread, volume, VWAP and order-book
imbalance, updated live; the producer status (running / paused / error, run number, requested and
actual rate) and a Pause / Resume control.

**Settings** — number of instruments (1–50), updates per batch (1–1,000) and interval (50–2,000 ms).
Editing the form never affects the producer; **Apply** starts a new run with fresh values and totals.

## Prerequisites

- **Node.js 24 LTS** (`24.22.1`, see `.nvmrc`). Angular CLI 22 needs `^24.15.0` or `>=26`.
- **pnpm 12** through Corepack (the exact version is pinned in `package.json` → `packageManager`):

  ```bash
  corepack enable pnpm
  ```

## Getting started

```bash
pnpm install
pnpm start          # dev server on http://localhost:4200
pnpm test           # all unit tests (Angular + compiled Wasm)
pnpm build          # production build into dist/
```

## How it works

Three layers, one job each. As little data as possible crosses the boundary between the worker and
the page.

```
Angular (main thread)            Web Worker                        WebAssembly
┌───────────────────────┐ start  ┌─────────────────────────┐ call ┌────────────────────────┐
│ Dashboard / Settings  │ pause  │ Scheduler               │─────▶│ Generator              │
│ read signals only     │ resume │ (setTimeout chain)      │      │ own PRNG, random walk, │
│                       │───────▶│                         │      │ state per instrument   │
│ MarketDataService     │        │ Aggregator              │◀─────│ output buffer          │
│ owns worker + runId   │◀───────│ totals per instrument   │ i32  │ 7 integers per update  │
└───────────────────────┘snapshot└─────────────────────────┘      └────────────────────────┘
```

**One batch, step by step**

1. The worker's scheduler fires (a `setTimeout` chain: the next batch is planned only after the
   current one has finished, so batches never overlap).
2. Wasm `generate(n)` writes `n` updates into its memory. The worker reads them through an
   `Int32Array` view — no JSON, no copying.
3. The aggregator folds every update into per-instrument totals, then the raw updates are dropped
   (no event history).
4. The worker posts **one snapshot** per batch: at most 50 rows plus the measured rate.
5. `MarketDataService` replaces its `rows` signal; the table re-renders. Main-thread work depends on
   the number of instruments, not on the update rate.

**A run** is one producer lifetime with fixed settings. The app starts run #1 with the defaults
(5 instruments, 100 updates, 500 ms). **Apply** terminates the worker and starts a new one with the
next run number; values and totals start from zero, and generation starts even if the previous run
was paused. Every message carries its `runId`, and the service drops anything from an older run —
a terminated worker can still have messages in the queue.

**Pause** stops scheduling in the worker; **Resume** continues one interval later from the same
totals. Nothing is generated for the paused time, and nothing is caught up afterwards.

**Navigation** keeps the run: the service is a root singleton that owns the only worker, so pages
come and go without creating another producer.

### Message protocol

Typed as discriminated unions in `src/app/core/protocol/messages.model.ts` and checked by type
guards on both sides of the boundary.

| Direction     | Type       | Payload                                                             |
| ------------- | ---------- | ------------------------------------------------------------------- |
| page → worker | `start`    | `runId`, `instrumentCount`, `updatesPerBatch`, `intervalMs`, `seed` |
| page → worker | `pause`    | —                                                                   |
| page → worker | `resume`   | —                                                                   |
| worker → page | `ready`    | `runId`                                                             |
| worker → page | `snapshot` | `runId`, rows (one per instrument), actual rate                     |
| worker → page | `error`    | `runId`, a message written for the user                             |

## Market data generator (WebAssembly)

The generator is written in [AssemblyScript](https://www.assemblyscript.org/) (`wasm/assembly/index.ts`)
and compiled to a ~1.3 KB module with **no imports**: random numbers (xorshift32) and price logic run
entirely inside Wasm.

- `init(instrumentCount, seed)` resets the state; `generate(n)` writes `n` updates into a buffer in
  Wasm memory and returns its address. Each update is 7 integers:
  `[instrument, priceCents, tradeQty, bidCents, askCents, bidQty, askQty]`. Symbols (`ALFA`,
  `BETA`, …) live in TypeScript; Wasm works with indices.
- Prices are integer cents and follow a random walk (±0.2 % per step) between $1 and $1,000. The
  bid is always below the ask, and each trade happens at the bid or the ask. Instruments are picked
  at random, so one batch can contain several updates for the same instrument.
- Tests (`wasm/test/`) load the **compiled** module with a fixed seed and check batch sizes, every
  invariant over 100,000 updates, determinism, and that the Wasm limits match the app settings.

## Testing

`pnpm test` runs 250 Angular unit tests (Vitest through the Angular CLI) and 23 tests against the
compiled Wasm module (Vitest in Node). No test waits in real time: timers are faked, the clock is
injected, seeds are fixed, and pages are tested with a fake worker or a stub service.

| Required by the task                                                      | Where                                                                                                                                |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Metrics: worked example, zero denominators, isolation between instruments | `worker/aggregator.spec.ts`, `shared/format/format.utils.spec.ts`, `features/dashboard/dashboard-columns.spec.ts`                    |
| Settings: validation, reset when applied                                  | `features/settings/settings-form.spec.ts`, `features/settings/settings-page.spec.ts`, `core/market-data/market-data.service.spec.ts` |
| Run control: pause/resume, rejecting previous-run results                 | `worker/batch-scheduler.spec.ts`, `worker/market-worker-runtime.spec.ts`, `core/market-data/market-data.service.spec.ts`             |
| Generator: requested batch sizes, valid values                            | `wasm/test/generator.spec.ts` (compiled module, fixed seed)                                                                          |

## Deployment

Every push runs [GitHub Actions](.github/workflows/ci.yml): install → lint → format check → tests →
production build. A green build of `main` is then deployed to GitHub Pages automatically; other
branches and pull requests only run the checks, so a broken change never reaches the live demo.

Two GitHub Pages details are handled by `pnpm build:pages`:

- The site lives under `/realtime-fintech-dashboard/`, so the app is built with that `--base-href`.
  The worker finds the Wasm file relative to its own script, so it works under any base path.
- Pages does not know Angular routes, so reloading `/settings` would return 404.
  `scripts/copy-404.mjs` copies `index.html` to `404.html`; Pages serves it for unknown paths, the
  app boots and the router shows the right page.

## Project structure

```
wasm/
  assembly/   AssemblyScript generator source
  test/       tests against the compiled module
src/app/
  core/       app-wide domain and singletons (MarketDataService, settings, message protocol)
  shared/     reusable UI components, form helpers and display formatting
  features/   pages: dashboard (table, producer status), settings (form)
  worker/     Web Worker: scheduler, rate meter, Wasm loader, aggregation
src/testing/  test-only builders, fixtures, fakes and stubs (never part of the app bundle)
src/styles/   design tokens, typography, mixins
```

File conventions, enforced by ESLint:

| File               | Contains                                            |
| ------------------ | --------------------------------------------------- |
| `*.model.ts`       | interfaces and types only                           |
| `*.constants.ts`   | constant values only                                |
| `*.utils.ts`       | pure functions                                      |
| `*.guards.ts`      | type guards for data crossing a boundary            |
| component / domain | logic (e.g. `aggregator.ts`, `app.ts`) and its spec |

- Imports across folders use path aliases (`@core/*`, `@shared/*`, `@features/*`, `@worker/*`,
  `@testing/*`); `../` imports are rejected. There are no barrel `index.ts` files: the app and the
  Web Worker are separate bundles, and a barrel that mixes worker-safe code with Angular services
  would pull Angular into the worker.
- Only spec files may import from `@testing/*`. Expected values stay written in the test itself.

## Tooling

- **Angular 22**: standalone components, zoneless change detection, signals, Signal Forms.
- **TypeScript 6.0**, strict mode (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, strict
  templates). TypeScript 7 is not yet supported by Angular 22.
- **AssemblyScript 0.28** for the WebAssembly generator.
- **Vitest** through the Angular CLI `unit-test` builder (jsdom), plus a Node config for the Wasm suite.
- **ESLint** flat config with angular-eslint and type-aware typescript-eslint rules; **Prettier**
  formats, ESLint checks logic (`eslint-config-prettier` turns off the overlapping rules).
- **Husky + lint-staged** lint and format staged files before each commit; **commitlint** enforces
  [Conventional Commits](https://www.conventionalcommits.org/).
