# Realtime Fintech Dashboard

An Angular application with a live market dashboard and producer settings. Simulated market data is
generated by a WebAssembly module (AssemblyScript) running inside a Web Worker.

> Work in progress. Architecture, decisions and the live demo link will be documented here as the
> project grows.

## Prerequisites

- **Node.js 24 LTS** (`24.22.1`, see `.nvmrc`). Angular CLI 22 needs `^24.15.0` or `>=26`.
- **pnpm 12** through Corepack (the exact version is pinned in `package.json` → `packageManager`):

  ```bash
  corepack enable pnpm
  ```

## Getting started

```bash
pnpm install
pnpm start          # dev server on http://localhost:4200
```

## Scripts

`start`, `build`, `build:pages` and `test` compile the WebAssembly generator first, so a fresh clone
needs no extra step. The compiled `public/wasm/generator.wasm` is a build artifact and is not
committed.

| Script              | What it does                                                      |
| ------------------- | ----------------------------------------------------------------- |
| `pnpm start`        | Run the dev server with live reload                               |
| `pnpm build`        | Production build into `dist/`                                     |
| `pnpm build:pages`  | Production build for GitHub Pages (see below)                     |
| `pnpm build:wasm`   | Compile `wasm/assembly/index.ts` to `public/wasm/generator.wasm`  |
| `pnpm test`         | All unit tests once: Angular suites, then the compiled-Wasm suite |
| `pnpm test:watch`   | Angular unit tests in watch mode                                  |
| `pnpm test:wasm`    | Only the generator tests, against the compiled module (Node)      |
| `pnpm lint`         | ESLint (TypeScript with type information, HTML, AssemblyScript)   |
| `pnpm format`       | Format all files with Prettier                                    |
| `pnpm format:check` | Check formatting without writing                                  |

## Market data generator (WebAssembly)

The generator is written in [AssemblyScript](https://www.assemblyscript.org/) (`wasm/assembly/index.ts`)
and compiled to a ~1.3 KB module with **no imports**: random numbers (xorshift32) and price logic run
entirely inside Wasm.

- `init(instrumentCount, seed)` resets the state; `generate(n)` writes `n` updates into a buffer in
  Wasm memory and returns its address. Each update is 7 integers:
  `[instrument, priceCents, tradeQty, bidCents, askCents, bidQty, askQty]`. JavaScript reads them
  through an `Int32Array` view — no JSON, no copying.
- Prices are integer cents and follow a random walk (±0.2 % per step) between $1 and $1,000. The
  bid is always below the ask, and each trade happens at the bid or the ask.
- Tests (`wasm/test/`) load the **compiled** module with a fixed seed and check batch sizes, every
  invariant over 100,000 updates, determinism, and that the Wasm limits match the app settings.

## Performance

Measured on the production build at the maximum settings — 50 instruments, 1,000 updates per batch,
50 ms interval (20,000 updates/s requested) — over 10 seconds in Chrome (desktop):

| Main thread busy                         | Long tasks (> 50 ms) | Frame rate | Heap         |
| ---------------------------------------- | -------------------- | ---------- | ------------ |
| ~14 % (script 2 %, layout + style 3.5 %) | none                 | 60 fps     | 6 MB, stable |

The main thread receives one small snapshot per batch (at most 50 rows), never individual updates,
so its work depends on the number of instruments, not on the update rate. The measured rate was
~17,400 updates/s: the interval is the _requested_ pause between batches, and each cycle also
includes the batch itself and timer delay. The producer status shows this actual rate next to the
requested one.

## Deployment

Every push runs [GitHub Actions](.github/workflows/ci.yml): install → lint → format check → tests →
production build. A green build of `main` is then deployed to GitHub Pages automatically; other
branches and pull requests only run the checks, so a broken change never reaches the live demo.

- Live demo: <https://arturkuz.github.io/realtime-fintech-dashboard/>
- Repository: <https://github.com/ArturKuz/realtime-fintech-dashboard>

Two GitHub Pages details are handled by `pnpm build:pages`:

- The site lives under `/realtime-fintech-dashboard/`, so the app is built with that `--base-href`.
- Pages does not know Angular routes, so reloading `/settings` would return 404.
  `scripts/copy-404.mjs` copies `index.html` to `404.html`; Pages serves it for unknown paths, the
  app boots and the router shows the right page.

## Project structure

```
src/app/
  core/       app-wide domain and singletons (MarketDataService, settings, message protocol)
  shared/     reusable UI components, form helpers and display formatting
  features/   pages: dashboard, settings
  worker/     Web Worker: scheduler, rate meter, Wasm loader, aggregation
src/testing/  test-only builders, fixtures and helpers (never part of the app bundle)
src/styles/   design tokens, typography, mixins
```

File conventions, enforced by ESLint:

| File               | Contains                                            |
| ------------------ | --------------------------------------------------- |
| `*.model.ts`       | interfaces and types only                           |
| `*.constants.ts`   | constant values only                                |
| `*.utils.ts`       | pure functions                                      |
| `*.guards.ts`      | type guards for data crossing a boundary            |
| component / domain | logic (e.g. `aggregator.ts`, `app.ts`) and its spec |

- Imports across folders use path aliases (`@core/*`, `@shared/*`, `@features/*`, `@worker/*`,
  `@testing/*`); `../` imports are rejected. There are no barrel `index.ts` files: the app and the
  Web Worker are separate bundles, and a barrel that mixes worker-safe code with Angular services
  would pull Angular into the worker.
- Only spec files may import from `@testing/*`. Expected values stay written in the test itself.

## Tooling

- **Angular 22**: standalone components, zoneless change detection, signals.
- **TypeScript 6.0**, strict mode (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, strict
  templates). TypeScript 7 is not yet supported by Angular 22.
- **Vitest** through the Angular CLI `unit-test` builder (jsdom).
- **ESLint** flat config with angular-eslint and type-aware typescript-eslint rules; **Prettier**
  formats, ESLint checks logic (`eslint-config-prettier` turns off the overlapping rules).
- **Husky + lint-staged** lint and format staged files before each commit; **commitlint** enforces
  [Conventional Commits](https://www.conventionalcommits.org/).
